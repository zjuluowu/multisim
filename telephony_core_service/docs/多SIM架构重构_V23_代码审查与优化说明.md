## 审查结论

V22 的主要设计方向合理：区分身份、位置、角色和资源；将事实、操作进度与兼容投影分开；为迟到响应和未知设备效果明确责任。当前最需要补强的是**论据的版本一致性、目标与实施状态的区分，以及可执行的迁移门禁**。

V23 保留原有领域设计与技术附录，优化为“当前事实 → 风险候选 → 目标责任 → 分阶段证据”。当前只能证明容量查询的 Linux 组件切片已运行，不能据此宣布状态与账户防护网、独立 SIM SO、公开服务入口或真实设备验收完成。

## 四项状态风险：当前能证明到哪里

### F01：事件处理与命令完成关联

`sim_state_handle.cpp:114–117` 将统计超时事件放入事件表；`:838–856` 在表内回调返回后进入相应同步完成通道；`sim_state_manager.cpp:171–194` 设置完成标志并通知等待方。因此“非命令技术事件可能参与通用完成”是有源码依据的风险候选。

PIN 有单独的 `SyncUnlockPinResponse` 与专用条件变量，不能泛化为所有 PIN 均会被统计超时误完成。其他命令在真实事件调度下是否受影响，仍需通过公开边界复现；本次未运行该反例。

### F02：状态日志映射

`enum_convert.h:350–356` 仅列出五种卡状态；`icc_state.h:29–36` 还定义 4–11。`sim_state_handle.cpp:409–411` 查找后未判断 `end()`，即将 `iter->second` 用作日志参数。该访问风险静态可见；可达输入和日志宏求值决定实际影响。本次不把它写成已发生崩溃。

### F03：同状态、不同身份

`sim_state_handle.cpp:408` 更新原始观测，`:420–422` 仅在状态变化时更新 `iccid_`。因此，同状态身份变化具有缓存更新风险。与此同时，`:635–687` 存在切换阶段与 `specifiedIccid_` 过滤，必须保留并核对场景前提；不能绕过过滤后将无依据输入归责生产。

### F04：加载轮次、计数与发布

`sim_file.cpp:180–265` 通过文件响应与计数推进完成；Records 通知发生于 LOADED 回写之前。`icc_file.cpp:775–783` 还会通过状态 Manager 写状态。这证明写入、加载和发布分布于多处；尚未证明旧轮响应已污染新轮缓存。目标 SessionRef/recordsGeneration 应在合法请求关联基础上实现，不能替代既有 RIL serial。

## SO 拆分还需做出的设计决定

1. **逐类归属与反向依赖**：分类审查 `CoreManagerInner` 的 SIM 内部回路、搜网查询、公共事件订阅和外部设备协作。跨模块能力通过注入端口表达，不能为消除链接错误把 SIM 业务逻辑改成 mock，也不能盲目把 Core 整体搬入 SIM SO。
2. **装配与停止**：保持 `CoreService::Init` 的既有初始化依赖；明确停止受理、注销、任务排空、回调拒绝与销毁顺序。现有 `OnStop` 不能直接被描述为已完成新工厂的 Stop 协议。
3. **C++ 边界**：InnerKit 接口不天然保证跨版本 ABI。至少确认创建/销毁方、异常边界、容器与分配器、符号可见性、CFI 跨 DSO、Feature 宏和全量重建策略。机械拆分与接口版本演进分别评审。
4. **拆分验收**：形成真实生产链接图和符号清单；禁止 Core↔SIM SO 反向循环。执行相同输入、权限、依赖配置下的 Legacy/Split 双版本边界测试；目前没有真实 Split 运行结果。
