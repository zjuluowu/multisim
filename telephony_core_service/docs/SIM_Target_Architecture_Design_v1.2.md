# SIM 目标架构设计

## 1. 文档定位与决策状态

### 1.1 目标

本文定义 SIM 管理功能完成 DDD 重构后的目标技术架构，重点回答：

1. 哪个上下文拥有哪个业务事实；
2. 哪个进程负责接纳命令和提交状态；
3. 何时向调用方、查询方和订阅方暴露结果；
4. 如何处理跨聚合、跨 SA、设备操作和持久化之间的一致性；
5. 如何处理迟到回调、重复请求、服务重启和结果不确定；
6. 如何让测试防护网跨内部架构变化持续复用。

目标不是仅将现有代码拆为 `libtel_sim_service.z.so`，而是建立稳定的领域职责和外部契约。

SO 拆分、目录迁移、类名变化均为实现手段，不构成领域边界的定义依据。

### 1.2 权威范围

本文负责：

- Bounded Context 到组件的映射；
- 分层及编译依赖；
- 聚合写入所有权；
- 进程与部署边界；
- 提交、可见性和通知协议；
- 持久化和恢复协议；
- 对外接口兼容策略；
- 基础设施与厂商扩展隔离；
- 架构规则及验证方式。

本文不直接定义：

- 统一语言及业务不变量：由 `SIM-DDD-001` 管理；
- 已发布外部契约：由 `SIM-BND-001` 管理；
- 现状代码事实：由现状分析和证据文档管理；
- 迁移顺序：由 `SIM-MIG-001` 管理；
- 具体测试用例：由 `SIM-TEST-001` 管理。

发生冲突时，不得通过修改本文件悄悄改变业务规则或已发布契约，应提交跨文档决策。

## 2. 架构目标与非目标

### 2.1 目标

1. Subscription 身份与位置、路由、Radio 资源分离。
2. 每类核心业务事实具有唯一受控写入协议。
3. 聚合内状态转换具有明确的一致性边界。
4. 跨聚合和跨 SA 协作显式处理失败与最终一致性。
5. 外部回调不能绕过身份、代次和状态门控。
6. 已提交事实与未完成操作具有不同的外部语义。
7. 旧 API 可以继续兼容，但不得反向决定核心领域模型。
8. 厂商扩展不能直接修改核心状态。
9. 领域测试跨 DDD 重构保留业务场景和断言。
10. 技术接入、运行时装配及存储实现允许受控演进。

### 2.2 非目标

- 不以一次版本完成所有新 Subscription API 的发布；
- 不强制采用 Event Sourcing；
- 不要求跨数据库、Modem 和 eUICC 建立全局原子事务；
- 不要求所有异步事件全局有序或恰好投递一次；
- 不以 Mock 替换核心业务来证明系统正确；
- 不将普通 Linux 受控测试等同于真实设备端到端测试。

## 3. 统一语义与身份规则

### 3.1 概念区分

| 概念 | 目标含义 | 禁止的默认等同 |
|---|---|---|
| Physical Endpoint | 硬件接入位置 | 不恒等于 API 中的 slotId |
| Logical Slot | 当前软件路由或兼容索引 | 不作为 Subscription 主键 |
| eUICC | 承载 Profile 的安全元件 | 不等于单个 Subscription |
| Port | eUICC 或设备提供的可用连接端口 | 不等于 Profile 身份 |
| Profile | 可管理的配置对象 | Disabled 不自动等于硬件不存在 |
| SubscriptionId | 系统中的业务身份标识 | 不由当前位置直接决定 |
| ICCID | 卡或 Profile 的身份相关属性 | 不未经确认就等同于所有场景下的主键 |
| Active / Enabled | 特定对象的激活或使能维度 | 不直接等于 Ready |
| Default Role | Voice/SMS/Data 等业务角色 | 不自动等于 Primary |
| Primary | 产品定义的主资源或主卡概念 | 不自动等于默认数据 |
| Radio Assignment | Subscription 与 Radio 资源的分配 | 不等于 Subscription 身份 |
| Readiness | 特定能力的就绪条件 | 不用一个 READY 覆盖所有初始化阶段 |

### 3.2 身份与生命周期

目标要求：

- 路由变化不应无依据地创建新业务身份；
- 位置复用不能让旧回调作用于新卡或新 Profile；
- 身份恢复、删除、重新发现和保留期限必须具有业务依据；
- 身份与别名的关联应可追溯；
- 测试使用 Card-A、Profile-B、Subscription-C 等业务别名，避免将固定 Slot 当作永久身份。

以下内容保持 OPEN：

- SubscriptionId 的生成与恢复规则；
- 卡移除后身份保留策略；
- 同一 Profile 再次启用时身份是否复用；
- 历史账户与当前 Subscription 的精确关系。

在这些问题确认前，不得把当前数组索引或数据库主键规则提升为领域不变量。

## 4. 目标上下文与唯一所有权

### 4.1 上下文划分

| Context | 核心职责 | 拥有的事实 | 不拥有的事实 |
|---|---|---|---|
| Subscription Topology | 发现、身份、位置和拓扑 | 已提交的拓扑及身份关联 | eUICC 操作执行状态、最终 Radio 分配 |
| Profile Operation | Profile 操作执行、关联、恢复 | 操作状态及操作结果证据 | 全局拓扑、最终业务角色 |
| Radio Resource | 角色和资源仲裁 | 已提交角色及 Radio 分配 | 卡硬件身份、Profile 内容 |
| Compatibility | 旧接口翻译与派生视图 | 兼容映射和接口状态，不拥有核心事实 | Topology、Operation、Assignment 的直接写权限 |

### 4.2 聚合所有权与部署

目标归属如下，以消除同名组件在两个 SA 中的歧义：

| 聚合 | 唯一逻辑写入者 | 目标部署 | 状态 |
|---|---|---|---|
| TopologyAggregate | TopologyManager | core_service SA | PROPOSED |
| OperationAggregate | OperationCoordinator | esim_service SA | PROPOSED |
| AssignmentAggregate | RadioResourceArbiter | core_service SA | PROPOSED |

约束：

1. `core_service` 不拥有可写的第二份 OperationAggregate。
2. `core_service` 可以持有操作结果的只读投影或关联信息，但不是操作事实来源。
3. `esim_service` 不直接修改 TopologyAggregate 或 AssignmentAggregate。
4. 跨 SA 结果通过显式集成协议进入接收方应用入口。
5. 同名组件的多个技术实例不得被误认为允许多写者。
6. 如果未来改变部署，必须重新审查跨进程交付、恢复和身份关联协议。

### 4.3 聚合边界依据

TopologyAggregate 暂以一个设备拓扑范围为候选一致性边界。

批准前必须验证：

- 哪些身份及映射不变量需要同一次提交；
- 无关卡并发是否会造成不必要的版本冲突；
- 多 Port、MEP 和特殊拓扑是否仍适用；
- 聚合快照是否足够轻量；
- 是否需要进一步拆分，以及拆分后如何保持业务规则。

不得仅因为当前存在 `data_[slotId]`，就认为所有拓扑事实必须永久属于一个大聚合。

6. Compatibility 是贯穿旧接口适配和只读投影的逻辑边界，不是第四个核心事实写入者。
7. 调度、时钟、执行队列和生命周期管理属于运行时支撑，不进入领域业务规则。
8. 应用层负责提交和恢复流程编排，领域层负责其中的业务合法性和状态转换，不能将业务规则全部移入应用服务。

#### 5.1.4 重构前后职责对比

| 维度 | 当前架构特征：待基线核验 | 目标架构约束 |
|---|---|---|
| 主要组织维度 | 以 Slot 及关联控制器组织多项流程 | 区分身份、位置、操作、角色及资源 |
| 服务入口 | 服务方法可能同时承担流程与状态处理 | 入站适配与应用编排分离 |
| 业务决策 | 分布在服务、控制器和辅助组件 | 由明确的领域所有者负责 |
| 状态写入 | 多处访问及更新路径需要梳理 | 每类事实具有唯一受控写入协议 |
| 异步回调 | 依赖现有请求及事件处理链 | 最终准入与状态转换原子衔接 |
| 版本控制 | 是否具备统一版本需核验 | 区分拓扑、分配、操作及请求代次 |
| 持久化 | 数据访问及系统参数分布于现有流程 | Repository Port 与明确提交协议 |
| 跨 SA 协作 | 依赖现有 IPC 及回调机制 | 显式关联、幂等、查询和恢复协议 |
| 旧 API | 与当前 Slot 模型紧密关联 | 经 Compatibility 翻译为正式命令和查询 |
| 厂商扩展 | 通过现有包装和动态库机制接入 | 能力查询、通知和业务命令分离 |
| 进程和 SO | 现有部署及库边界 | 不以进程或 SO 替代领域职责边界 |
| 测试 | 容易绑定内部对象和调用顺序 | 稳定业务场景，技术适配可变 |

#### 5.1.5 不以“增加层数”作为完成标准

本次重构不要求为每一层机械新增包装类，也不要求所有调用都穿过无业务意义的转发链。

分层成立的判断标准是：

- 对外协议变化不直接污染核心业务规则；
- 核心领域不依赖具体基础设施；
- 业务事实的所有权和写入路径明确；
- 异步操作具有版本、提交及恢复语义；
- 旧接口和厂商扩展不能绕过核心规则；
- 测试能跨内部结构变化复用业务场景和断言。

从现有组件到目标组件的具体迁移步骤，由 `SIM-MIG-001` 管理，不在本节以逐类搬迁替代领域设计。

### 5.2 编译依赖

- Domain 不依赖具体 DB、RIL、IPC、SA、FFRT 或动态库实现。
- Application 依赖 Domain 和抽象 Port，不直接依赖具体适配实现。
- API 和入站适配器调用 Application 入口。
- Infrastructure 实现抽象 Port。
- 装配层负责连接接口与实现。
- Port 按用途归属于 Domain 或 Application，不强制所有技术接口都放入 Domain。

### 5.3 运行时规则

- 入站 RIL/eUICC 回调可以经适配器调用应用入口。
- 领域业务通过出站 Port 请求外部能力。
- 禁止适配器绕过应用入口，直接修改聚合内部状态。
- 禁止跨聚合共享可写引用。
- 跨聚合反馈可以发送正式命令，但不得直接回写发布者状态。

### 5.4 Compatibility 的准确约束

Compatibility 不得：

- 直接写核心 Repository；
- 修改聚合内部状态；
- 将派生视图写回核心；
- 自行实现角色分配或身份决策。

Compatibility 可以：

- 将旧查询翻译成正式 Query；
- 将旧写 API 翻译成正式 Command；
- 转换返回值、错误码和公开事件格式。

`LegacySlotView` 严格只读；“旧命令翻译”不是只读视图的一部分。

## 7. 部署与跨 SA 协作

### 7.1 目标部署

```text
core_service SA
├─ 公开 Core/SIM API 与旧接口适配
├─ Topology 应用服务及聚合
├─ Radio Resource 应用服务及聚合
├─ 进程内领域事件分发
├─ 存储、RIL、参数及厂商适配
└─ eSIM 集成客户端 / 接收端

             显式 IPC 集成协议
                      ↕
esim_service SA
├─ eSIM API 与应用服务
├─ OperationCoordinator
├─ OperationRepository
├─ 进程内领域事件分发
└─ eUICC 适配
```

不新增 SA 是本轮目标约束。

具体 ability 编号、SA Profile、动态库名称和安装关系，需按 `SIM-SA-001` 与基线核验后确定。

### 7.2 跨 SA 不是进程内事件总线

跨 SA 使用显式集成协议，不能直接假设共享：

- 聚合实例；
- 内存引用；
- Domain Event Bus；
- 锁；
- 单一事务；
- 事件全局顺序。

跨 SA 消息至少需要表达：

- 协议版本；
- 消息或结果标识；
- OperationId / 关联标识；
- 目标业务身份；
- 操作代次或执行上下文；
- 结果及必要证据；
- 接收方判断适用性所需的版本信息。

精确字段在接口契约中定义，不能只依赖 slotId。

### 7.3 交付与恢复

不假设恰好一次投递。

协议必须支持：

- 重复通知的幂等接纳；
- 丢失通知后的结果查询或状态对账；
- SA 退出和重连；
- 旧通知到达新会话；
- 调用超时但操作仍在执行；
- 接收方退出后恢复。

可选择持久待发送记录，或采用持久结果记录加重新查询。

在实现评审前必须证明所选方案不会永久丢失必要结果；仅有内存异步事件队列不满足恢复要求。

## 8. 状态所有权、Repository 与查询

### 8.1 单一事实来源

每个聚合具有一个受控写入流程：

- 聚合负责业务合法性；
- 提交协调负责并发版本与提交协议；
- Repository 负责装载和保存；
- 已提交内存快照负责正常运行时的核心查询；
- 持久记录负责需要持久化的重启恢复；
- 派生缓存不具有独立业务写权限。

Repository 适配器不得维护另一套可独立改变业务状态的缓存。

### 8.2 查询分类

| 查询 | 语义 |
|---|---|
| 核心事实查询 | 读取已提交状态 |
| 操作状态查询 | 返回接纳、执行、恢复及终态 |
| 硬件观察查询 | 返回最近观测及其有效性，不冒充已提交业务分配 |
| Compatibility 查询 | 从核心事实派生，必要时标明版本或就绪情况 |

不允许用一个布尔 `ready` 同时表示服务存在、卡就绪、账户完成和 Radio 可用。

### 8.3 跨聚合读取

Topology 与 Assignment 不默认具有分布式原子快照。

需要组合查询时必须：

- 携带各自版本及关联拓扑版本；或
- 通过协调查询判断组合是否有效；或
- 明确返回重新协调中、未就绪等状态。

不得将两次独立读取自动解释为同一时刻的一致事实。

## 9. 提交与外部可见性

### 9.1 Commit 定义

本文将“核心业务提交”定义为：

> 必要校验通过，按该类状态要求完成持久化或内存提交，并发布为可查询的已提交版本。

需明确区分：

1. 请求已接纳；
2. 外部动作已发出；
3. 外部动作已有结果；
4. 核心业务状态已提交；
5. 对外通知已送达。

这些阶段不得统一称为“成功”。

### 9.2 状态转换的执行方式

目标采用每聚合受控执行通道，避免并发写入。

一次需要持久化的状态转换按以下阶段执行：

1. 读取已提交版本并构造候选变更；
2. 校验业务条件及相关版本；
3. 在不持有领域锁的情况下执行存储 I/O；
4. 必要时通过条件提交防止旧版本覆盖；
5. 将成功提交的候选状态发布为内存已提交快照；
6. 产生提交后通知；
7. 处理通知失败或恢复记录。

在该转换完成前，其他变更排队或按明确协议拒绝。

若采用多个并发候选提交，必须另行定义冲突检测和重试，不能只依赖一次加锁读取。

### 9.3 可见性规则

- 未提交候选状态不得通过普通核心查询暴露。
- 运行中的操作可以通过操作查询暴露为 PENDING 等非终态。
- 硬件已经变化但本地尚未协调完成时，应允许表达“观测变化、协调中”。
- 不得宣称硬件副作用与数据库提交具有全局原子性。
- 对外成功通知必须对应其声明范围内已经完成的事实。

### 9.4 崩溃窗口

必须覆盖：

| 崩溃位置 | 恢复要求 |
|---|---|
| 持久化前 | 不恢复为已提交成功 |
| 持久化后、内存发布前 | 从持久记录恢复已提交状态 |
| 状态提交后、通知前 | 通过补发或查询对账恢复观察一致性 |
| 硬件动作后、本地结果记录前 | 查询真实设备状态，不能直接推断失败 |
| 通知送达后、本地确认前 | 重投不得造成重复业务副作用 |

### 9.5 不使用全局事务掩盖问题

Topology、Operation、Assignment 和设备状态之间通过显式协调达到约定一致性。

需要分别定义：

- 哪些条件必须始终成立；
- 哪些条件允许在收敛窗口后成立；
- 哪些中间状态可以公开；
- 哪些故障必须进入恢复流程。

## 10. 版本与过期决策处理

### 10.1 版本区分

| 标识 | 用途 |
|---|---|
| TopologyRevision | 拓扑提交版本 |
| AssignmentRevision | 分配提交版本 |
| BaseTopologyRevision | 某次决策所依据的拓扑版本 |
| OperationVersion | 操作状态转换版本 |
| RequestAttempt / Generation | 区分重试、步骤或生命周期代次 |

版本的持久化及重启延续策略必须定义，不允许隐含依赖进程内计数器永不重置。

### 10.2 决策执行前后校验

Radio 决策至少在两个阶段校验：

1. 发出外部动作前；
2. 接纳外部结果并提交分配前。

拓扑版本变化不必一律使操作失败，但必须判断：

- 目标身份是否仍存在；
- 路由、Port 和资源是否仍匹配；
- 变化是否影响原决策；
- 已发生副作用是否需要重新协调。

允许结果：

- 继续提交；
- 重新仲裁；
- 拒绝过期结果；
- 执行恢复或补偿；
- 标记结果未确定并等待对账。

仅“读取同一 Revision”不足以证明执行结果有效。

## 11. 回调准入与幂等

### 11.1 关联信息

根据操作类型，回调关联应能区分：

- OperationId；
- 步骤或请求标识；
- 请求代次；
- 目标 Subscription/Profile；
- 当前路由或通道绑定；
- 服务或执行会话；
- 相关版本。

字段可以由适配层保存关联表补足，不要求底层接口天然返回全部字段，但必须说明关联失效后的处理方式。

### 11.2 原子接纳

回调处理流程：

1. 进行格式及权限等预校验；
2. 进入目标聚合的受控执行通道；
3. 在同一并发控制边界内完成最终准入判断和状态转换；
4. 执行必要提交；
5. 发布提交后的结果。

预校验不能替代最终校验。

### 11.3 重复与迟到

- 重复成功回调不得重复执行业务副作用。
- 旧操作回调不得改变新操作。
- 旧卡回调不得改变复用相同 Slot 的新卡。
- 已终结操作收到回调时按协议忽略、记录或触发对账。
- 无法确认关联的回调不得按当前 Slot 直接推断目标。

## 12. Profile 操作与恢复

### 12.1 操作状态

以下是技术状态候选，正式业务状态由领域文档确认：

- ACCEPTED；
- EXECUTING；
- RECONCILING；
- SUCCEEDED；
- FAILED；
- CANCELLED；
- COMPENSATING；
- COMPENSATED；
- MANUAL_RECOVERY_REQUIRED。

不能仅用 ABORTED 表示所有服务退出场景。

### 12.2 操作成功的范围

必须区分：

- eUICC 设备操作已经完成；
- 拓扑已经重新发现并提交；
- 角色及 Radio 已完成协调；
- 整个调用方场景已经完成。

若 API 只保证其中一层，必须明确声明，不能用一个成功回调隐含全部完成。

### 12.3 持久化分级

| 操作类别 | 要求 |
|---|---|
| 无外部副作用且允许丢失 | 可以采用纯内存记录 |
| 存在设备副作用 | 应保存足够的恢复关联信息 |
| 调用方需要跨重启查询 | 必须保留可查询结果或可恢复记录 |
| 涉及补偿 | 必须记录已完成步骤及补偿进度 |

### 12.4 重启恢复

重启后：

1. 装载需要恢复的操作；
2. 建立新的执行会话；
3. 查询设备或依赖服务事实；
4. 判定已完成、可重试、需补偿或结果未知；
5. 更新操作状态；
6. 向相关上下文发送可恢复的结果通知。

不能因进程退出就自动认定外部动作未执行。

## 13. 持久化模型

### 13.1 存储职责

| Repository | 保存内容 | 目标要求 |
|---|---|---|
| TopologyRepository | 身份、映射及恢复所需拓扑事实 | 原子提交及版本条件 |
| OperationRepository | 恢复必需的操作上下文和结果 | 按操作类别分级持久化 |
| AssignmentRepository | 角色和资源分配事实 | 一次决策的完整提交 |

### 13.2 存储决策

PROPOSED：

- Topology 使用支持事务或等效原子提交能力的持久化适配；
- 需要持久化的 Assignment 使用可证明完整提交的存储协议；
- 系统参数可以作为兼容输出，不默认作为多字段分配的唯一权威存储；
- 存储介质的最终选择在能力验证后批准。

不能仅因“已有系统参数接口”就推断多个键可以原子更新。

### 13.3 数据结构约束

- Subscription 以业务身份检索，不以 slotId 作为身份主键。
- 路由、Slot、Port 是属性或关联。
- TopologyRevision 与 AssignmentRevision 分开。
- Assignment 记录其依据的拓扑关联信息。
- 操作记录不直接覆盖拓扑事实。
- 内部表、索引和序列化格式不构成外部契约。

### 13.4 故障行为

存储失败时必须定义：

- 请求是拒绝、待恢复还是可重试；
- 已发生设备副作用如何协调；
- 查询看到哪个已提交版本；
- 是否允许发布失败或恢复中事件；
- 如何避免重试造成重复执行。

---

## 14. 线程与执行模型

### 14.1 基本约束

- 每聚合具有受控的写入执行通道。
- 锁只保护必要的内存访问。
- 领域锁内不执行 DB、RIL、APDU、IPC 或厂商回调。
- 外部回调线程不直接修改聚合。
- 事件分发不持有发布者领域锁。
- 不以跨聚合共享锁实现事务。

FFRT 是候选生产调度实现，不是领域接口的一部分。

### 14.2 I/O 与执行通道

“不持有锁执行 I/O”不意味着允许无序并发提交。

可以在逻辑串行通道中异步等待 I/O，但必须处理：

- 队列长度；
- 超时；
- 取消；
- 进程退出；
- 高优先级事件；
- 回调重入；
- 饥饿和背压。

不得将领域状态一致性寄托于线程池恰好按某种顺序执行。

### 14.3 通知顺序

按聚合或业务流定义必要偏序。

不承诺所有 Context、所有进程、所有订阅者之间的全局顺序。

---

## 15. 事件与集成通知

### 15.1 三类消息

| 类别 | 作用 | 稳定性 |
|---|---|---|
| Domain Event | 进程内领域协作 | 可以随内部模型演进 |
| Integration Notification | 跨 SA 或跨服务协作 | 需要版本、关联和恢复协议 |
| Published External Event | 对外公开行为 | 受已发布契约约束 |

三者不能直接共用同一个“事件目录”而不标明语义。

### 15.2 候选领域事件

可包括：

- TopologyChanged；
- SubscriptionDiscovered；
- SubscriptionRemoved；
- OperationStateChanged；
- RoleAssignmentChanged；
- ResourceAssignmentChanged。

名称和载荷为内部设计候选，不作为长期黑盒测试断言。

### 15.3 事件约束

- 已提交事实通知在对应提交后产生。
- 单调版本只在声明的作用域内成立。
- 消费方不得直接修改发布者状态。
- 消费方可以通过正式命令反馈业务需求。
- 处理必须考虑重复、遗漏、乱序及恢复。
- Event Sourcing 是否采用，与事件可靠通知是两个独立决策。

## 16. API 与兼容协议

### 16.1 旧 API

旧接口继续通过适配层提供。

适配层负责：

- 参数校验与语义翻译；
- slotId 到当前业务目标的解析；
- 错误码及回调格式转换；
- 兼容查询投影。

不负责核心业务策略。

### 16.2 旧写命令的目标绑定

必须定义目标解析时点。

PROPOSED：

- 命令接纳时解析并绑定目标业务身份及必要路由版本；
- 执行前再次验证绑定仍适用；
- 不得在 Slot 被新对象复用后，静默将旧命令重定向到新对象。

对于历史接口本身明确表示“执行时当前位置”的情况，应单独记录契约，不能统一套用身份绑定规则。

### 16.3 新 Subscription API

新接口围绕业务身份设计，但不自动替代所有卡硬件接口。

应明确：

- 同步接纳结果；
- 异步终态；
- OperationId；
- 查询和取消能力；
- 重试与幂等语义；
- 权限；
- 生命周期与结果保留；
- 错误码；
- 版本兼容。

不得直接修改旧 IPC 方法签名而省略兼容策略。

## 17. PSIM/eSIM 与厂商差异隔离

### 17.1 差异隔离

统一的是业务语义，不是强行统一所有技术过程。

- EF 与 APDU 的传输差异留在适配层；
- Profile 与物理卡的生命周期差异由对应业务模型表达；
- MEP 的 Port 和多关联能力必须显式建模；
- 初始化与重试策略不得隐藏业务状态；
- 产品差异通过能力和策略输入表达，不散布硬编码数量判断。

`ICardChannel` 是否覆盖全部文件操作仍为 OPEN，不应在范围未定时成为迁移阻断式抽象。

### 17.2 厂商扩展分为三类

1. 能力查询：提供产品能力及限制。
2. 结果通知：接收已提交业务变化。
3. 业务命令：通过正式应用入口提出修改请求。

厂商实现不得：

- 持有核心聚合可写引用；
- 修改核心 Repository；
- 包含核心内部实现头；
- 在通知回调中隐式完成核心业务决策。

### 17.3 动态库边界

必须定义：

- 接口版本与能力协商；
- 加载失败和符号缺失；
- 数据所有权及释放方式；
- 线程和重入要求；
- 错误及超时；
- 类型布局和 ABI 策略。

仅使用 POD 类型不足以单独证明 ABI 兼容。

## 18. 架构规则与验证方式

保留原规则编号，但以下表述需与规则目录同步评审。

| 规则 | 修订后的约束 | 主要验证方式 |
|---|---|---|
| ARCH-RULE-001 | 业务身份不以 slotId 定义；位置是关联属性 | 模型评审、静态检查、身份场景测试 |
| ARCH-RULE-002 | 核心事实具有唯一受控写入协议；禁止跨聚合直接写入 | 接口检查、依赖检查、并发测试 |

| ARCH-RULE-004 | 外部回调经过原子准入与状态转换 | 重复、迟到、错身份回调测试 |
| ARCH-RULE-005 | Compatibility 不直接写核心事实；允许正式命令翻译 | 静态检查、旧 API 契约测试 |
| ARCH-RULE-006 | Domain 不依赖具体基础设施 | 编译依赖检查 |

| ARCH-RULE-010 | 容量与拓扑能力统一查询，禁止散布固定数量假设 | 静态检查、多拓扑测试 |

## 19. Linux 测试防护网与 DDD 复用

### 19.1 测试分层

| 层次 | 目标 |
|---|---|
| 领域行为受控边界测试 | 真实 services 业务实现及外部协作 |
| 已发布接口契约测试 | API、错误码、回调和公开事件 |
| 架构适应度检查 | 依赖、越层、写入入口及锁约束 |
| 部署与设备测试 | 真实 IPC、SA、权限、Modem、eUICC |

### 19.2 Linux 工程

使用独立 GN + Clang + GoogleTest 工程。

不得依赖现有 `test/` 的：

- Mock；
- Fixture；
- 测试目标；
- 测试静态库；
- 生产源码重编译清单。

允许外部组件 Fake/Spy，不允许替换被测的身份、账户、角色和恢复决策。

是否能形成可信生产运行闭包，必须先调查，不在本文中宣称已经可执行。

### 19.3 稳定与可变部分

DDD 重构后应保持：

- 业务场景；
- Contract ID；
- 已确认 Invariant ID；
- 目标与非目标对象的影响约束；
- 业务最终状态及失败恢复期望。

允许调整：

- 入口绑定；
- 启动与装配；
- 外部组件替身；
- 技术查询适配；
- 调度和进程测试设施。

内部类名、Repository 方法和领域事件名称不得成为长期业务断言。

### 19.4 优先保护场景

1. 路由变化而业务身份保持。
2. Slot 复用后旧回调不污染新身份。
3. 旧拓扑决策不能错误提交新分配。
4. 存储失败不发布虚假成功。
5. 提交后通知丢失仍能恢复观察一致性。
6. eUICC 副作用后重启能重新协调。
7. 旧命令不因映射变化误操作新卡。
8. 重复请求与回调不造成重复副作用。
9. 非目标 Subscription 不受错误影响。
10. 多 Port、多 Profile 与资源受限场景具有正确结果。

### 19.5 Oracle 分类

测试断言必须区分：

- CONFIRMED_CONTRACT；
- VERIFIED_INVARIANT；
- LEGACY_BEHAVIOR；
- OPEN_QUESTION。

本文的 PROPOSED 决策在批准前不能自动成为生产验收强断言。

## 24. 总结

目标架构的正确性不取决于组件名称、逻辑层数量或动态库数量，而取决于：

- 事实所有权是否唯一；
- 身份是否独立于位置；
- 决策是否基于有效版本；
- 成功与提交是否有清晰边界；
- 失败和结果未知是否可恢复；
- 兼容层和厂商扩展是否受控；
- 测试是否保护长期业务契约。

当前架构与目标架构的对比图用于解释职责如何演进，不替代源码证据、领域模型或一致性协议。

重构可以改变系统内部如何完成工作，但不能未经批准改变系统对外应当完成什么。
